# Phase I as-of prospective factor grid: incremental replay contract

The original `lab/phase1_warehouse_asof_grid.py` rejoined **every historic captured event market** to the entire allowed observed Treasury factor panel at every execution. With more than 40,000 cumulative receipt-time markets, repeated all-history candidate generation and row-number windows increase MotherDuck compute time and can exhaust the organization's included Flight allowance, even when there are only a few thousand *new* market receipts.

The source-controlled update makes the normal run **incremental by original capture identity**, not by ticker, display title, date or market alone. Only `(run_id, venue, market_id)` not already represented in the append-only grid is considered for the expensive as-of factor join. All prior grid rows remain unchanged; only candidate factor keys absent from the immutable source table are appended transactionally. It continues to require factor `source_ingested_at <= event known_at` and factor `source_availability_at <= event known_at` and rejects any future warehouse information before persistent writes. A no-new-data rerun should produce zero new factor-grid keys. No original exchange-quote or economic-release publication clock is inferred.

**Explicit full replay:** if eligible source families, factor catalog permissions, source publication/ingestion timestamps, or the event-factor relationship rules change and historic captures must be reconsidered, run the producer with `LAB_GRID_FULL_REPLAY=true` plus `LAB_RESEARCH_SCOPE=internal-only` and the exact Git commit `LAB_PIPELINE_COMMIT`. The default `LAB_GRID_FULL_REPLAY=false` skips *previously materialized* capture-market identities and is **not a replacement for a full audited historical source reconciliation**. A partially represented prior event/factor cohort is not completed by the fast path unless that operator explicitly invokes the full replay. Neither mode overwrites the original source or existing grid records.

The attached in-memory DuckDB contract tests establish correct replay flags, distinct venue/run/market identities, zero incremental rerun candidates and original source temporal safeguards. Both modes should report staged original capture-market count and execution mode. No benchmarked wall-clock improvement or new MotherDuck Flight success should be claimed before the new source revision is deployed and independently executed: the speed rationale is the narrower query shape, not a measured production timing guarantee.

## Release chain

The main manual GitHub Actions workflow `phase1_prospective_capture.yml` still performs original two-venue capture, research features, grid build, explicit newest capture-to-grid reconciliation, source inventory and original-publication clock audits, then institutional gate evaluation and blocker registration, using a scoped MotherDuck secret. The finite daily MotherDuck Flight allowance is separate from GitHub Actions compute and secret availability; avoid concurrent runs. Institutional production risk approvals remain false regardless of faster warehouse receipts.
